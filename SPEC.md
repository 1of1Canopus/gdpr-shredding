# SPEC — Module C · GDPR Shredding (erasure by key destruction for JPA)

Status: READY. Second module (4 weeks).

## Why (plain words)
When a person asks to be forgotten, GDPR says delete; audit, accounting and AML rules say keep records. Crypto-shredding resolves it: encrypt each person's personal fields with that person's own key; to erase, destroy the key. The EDPB, CNIL and ICO accept this. In Java there are only blog posts and an Axon event-store extension. No Spring/JPA starter exists.

## Free core (`gdpr-shredding-core`)
1. `@Shredded(subject = "#{owner.id}")` on entity fields (String, byte[], LocalDate, BigDecimal, JSON) → JPA `AttributeConverter`s generated/registered per type; the **data subject id** resolved from an SpEL expression or a `SubjectResolver` bean.
2. Envelope encryption: per-subject data key (AES-256-GCM, random 96-bit nonce per value, AAD = entity+field+subject) wrapped by a master key from a `KeyProvider` SPI. Core ships `JdbcKeyProvider` (keys table, wrapped with a master key from env) and `InMemoryKeyProvider` (tests).
3. `ErasureService.erase(subjectId)`: destroys the subject's data key (overwrite + delete), writes an `ErasureRecord` (append-only, hash-chained: subject id hash, requested by, reason, timestamp, affected entity/field counts) and, optionally, runs registered `PostErasureHook`s (e.g., anonymise search indexes).
4. Reads after erasure return a typed `ErasedValue` sentinel (configurable: null, placeholder, or exception) so the rest of the app keeps working with audit rows intact.
5. Searchability helper: optional blind index (HMAC of a normalised value with a per-tenant key) for equality lookups on encrypted fields (`@BlindIndex`).
6. Auto-config, properties `shredding.*`, sample app: a customer entity with encrypted email/phone, an audit table that keeps `customer_id`, an erasure endpoint, and a test proving the row persists but cannot be decrypted.

## Pro edition (`gdpr-shredding-pro`)
- Key providers: HashiCorp Vault Transit, AWS KMS, Azure Key Vault, GCP KMS; master-key rotation with re-wrap job; key escrow policy.
- Per-tenant master keys (Tenantify integration); per-tenant erasure.
- Erasure workflow: request intake → identity verification hook → grace period → erasure → **proof-of-erasure PDF/HTML** for the DPO (what, when, who, hash chain reference).
- Admin UI: subjects, keys, erasure log, verification endpoint; retention rules (auto-erase after N days for a category).
- Migration tool: encrypt existing columns in batches with progress + resume.
- Price: €390 per app · €790/yr team.

## Domain model
`SubjectId` · `DataKey {subjectId, version, wrappedKey, createdAt, destroyedAt}` · `ErasureRecord` · `EncryptedValue {version, nonce, ciphertext, tag}` (self-describing binary format with a version byte; document the format).

## Threats
Key material in heap dumps/logs (zeroise byte arrays; never `String` for keys; log-scan test); nonce reuse (random per value, test for uniqueness at scale); AAD omission (entity/field binding mandatory); backups containing keys (docs: back up the keys table separately, or use KMS); erasure race with in-flight writes (erase marks key `DESTROYING` first; writes fail with typed error); master-key loss (docs + `--dry-run` check in a startup health indicator); a write racing an erasure that finds the key row already deleted and mints a fresh key for the erased subject, undoing the erasure with nothing in the log to say so (closed by the `shredding_erased_subject` tombstone, which holds no key material; Dollar's ruling on QUESTIONS #3, 2026-09-08).

### Cipher spec review (2026-09-08)

Crypto-shredding is a *key-management* product wearing an encryption costume: the ciphertext is irrelevant, the only real asset is the non-recoverability of one key. Everything below follows from that, plus module B's ruling — no security control ships as "optional when set", and there is no backward compatibility on an unreleased branch.

**Controls.** Secure mode is the default; every weaker mode is an explicit property that logs a WARN at *every* startup, not only the first. There is deliberately **no fail-open property anywhere in this module.**

1. **Data keys are random, never derived.** `SecureRandom` 256-bit per (tenant, subject, version). A `HKDF(master, subjectId)` design would make erasure a no-op for anyone holding the master — the key is re-derivable forever. The `KeyProvider` SPI contract states this; `InMemoryKeyProvider` refuses to start unless `shredding.dev-mode=true` (default `false`, WARN when on).
2. **AAD is length-prefixed and canonical**, B's `ag1|<len>:<value>` form: `sh1|version|alg|tenant|subject|entity|field|keyVersion`. Unprefixed concatenation lets `entity="Custom"+field="erEmail"` collide with `entity="Customer"+field="Email"`. AAD is mandatory, never configurable, never empty.
3. **Nonce.** Random 96-bit from `SecureRandom` (a persisted counter cannot be made safe across a converter with no transaction coordination — a rolled-back counter is a catastrophic GCM reuse). Bound it instead: a per-key encryption count in the key row, WARN at 2^31, hard refusal at 2^32 (`shredding.crypto.max-encryptions-per-key`, default `4294967296`, values above it rejected at startup) → auto-rotate to key version n+1. GCM tag is 128 bits, not configurable.
4. **`EncryptedValue` is a strict format**: magic + version byte + alg id + key version + nonce + ct||tag, fixed offsets, stored in `bytea`. An unknown version, a truncated blob, or trailing bytes is a typed error — never a best-effort parse, never a plaintext fallback.
5. **Master key.** `shredding.master-key`, required, env only, base64, ≥32 bytes, no default, sample values rejected at startup; read as `byte[]` and zeroised, excluded from actuator `/env` and `/configprops` explicitly (not by name-sanitisation luck); never in exception messages, metrics tags or `toString`. Wrapping is AES-256-GCM with AAD = tenant|subject|keyVersion, so a wrapped-key row cannot be swapped between subjects.
6. **Erasure is a delete of the key row, in one transaction with the erasure record.** Not "overwrite + delete": on MVCC the overwrite only creates a second heap tuple holding the same key, and the assurance it implies is false. `SELECT … FOR UPDATE` on the key row, idempotent, so a repeat erase is a no-op and not a second record. A destroyed key with no record (unprovable erasure) or a record with a live key (false proof) must both be impossible.
7. **Key cache is bounded and short.** `shredding.data-key-cache.ttl` default `60s`, `.max-size` default `10000`. Erasure evicts locally and publishes an invalidation; other nodes still hold the unwrapped key for up to the TTL — that window is documented and appears in the proof-of-erasure. `DESTROYING`/`DESTROYED` is checked on **read** as well as write.
8. **Erasure record chain = module B verbatim.** Keyed from row 1, key id inside the hashed material, length-prefixed canonical form, external anchor row, triggers refusing UPDATE/DELETE/TRUNCATE, statuses `EMPTY`/`INTACT`/`INTACT_UNKEYED`/`BROKEN`/`ANCHOR_MISMATCH`/`NO_ANCHOR`. `shredding.erasure-log.hmac-secret` required, `.hmac-key-id` default `k1`, `.hmac-keys.<id>` keyring, `.unkeyed=true` the WARNed opt-out. This key is **not** a data key and is **never destroyed by an erasure** — destroying it would break the very record that proves the erasure.
9. **Subject pseudonym is HMAC, not SHA-256.** The spec's "subject id hash" over an email or a UUID is enumerable in seconds. HMAC with a pepper derived by HKDF from the erasure-log secret, info `sh/subject-pseudonym/v1` — same secret, provably separated domain, one fewer secret to lose.
10. **Blind index.** Its own secret `shredding.blind-index.hmac-secret` (required when any `@BlindIndex` exists), per-tenant subkey by HKDF info `sh/blind-index/v1|<tenantId>`, never the data-key or chain material. It is a **prefilter**: truncated to `shredding.blind-index.bits` (default `64`) and the query path always re-verifies by decrypting. Normalisation (NFKC, casefold, trim, per-type rule) is versioned in the index prefix and runs in one code path shared by write and query. **Erasure nulls the subject's blind-index columns** — non-negotiable and not a property: an index that survives erasure keeps the erased subject searchable and linkable forever, which defeats the entire product.
11. **`ErasedValue` cannot be re-encrypted.** `convertToDatabaseColumn` refuses a subject whose key is `DESTROYING`/`DESTROYED` (`SHRED-ERASED-001`), *and* the sentinel round-trips to byte-identical stored bytes so Hibernate dirty checking sees no change and never rewrites the column. Both, not either.
12. **Plaintext leak paths are closed at startup, not by convention.** A `@Shredded` entity that is `@Cacheable`/`@Cache` fails startup unless `shredding.allow-second-level-cache=true` (default `false`, WARN). Query cache likewise. `ErasedValue.toString()` is a fixed marker; a `@Shredded` field appearing in a generated `toString`/`equals`/`hashCode` or in a Jackson-serialised entity is flagged by the module's ArchUnit rule, and the sample ships a log-scan test grepping for the plaintext fixture.
13. **`shredding.erased-value.policy`** default `sentinel`; `exception` allowed; `null` is a silent-failure mode and requires the value `null` plus a WARN at every startup. Not per-read, not per-call — one policy per application.
14. **SpEL runs in a `SimpleEvaluationContext`** (property read-only: no bean references, no `T()` type refs, no constructors, no method invocation), parsed once at bootstrap with a parse failure failing startup. The resolved subject id is validated (non-blank, bounded length, charset) and only ever reaches SQL as a bind parameter. **The subject id is captured at first persist and immutable**: a later change would silently re-encrypt the row under another subject's key and move it out of the erasure scope — refuse with a typed error.
15. **Tenant is mandatory and fails closed.** Key table PK `(tenant, subject, version)`; tenant in the wrap AAD, the value AAD, the blind-index subkey and the erasure record. No "default tenant" fallback; a missing tenant context is an error, not an empty string.
16. **Key store down ≠ erased.** The SPI distinguishes `KEY_UNAVAILABLE` (retryable, 503, health indicator DOWN) from `KEY_DESTROYED` (terminal, `ErasedValue`). Conflating them turns a KMS outage into an apparent completed erasure — and, with control 11 absent, into a real one. No indefinite stale-cache fallback, no plaintext fallback, no property to enable either.
17. **Core must not migrate plaintext.** No backfill, no "decrypt, else return the column as plaintext" fallback — that is a downgrade oracle and the worst possible half-state. Core refuses to read a `@Shredded` column whose bytes are not in the control-4 format. The batch migrator is Pro-only, resumable, per-batch transactional, and drops the plaintext column only after a verification pass.
18. **Supply chain: JDK-only crypto in core.** AES-256-GCM, HMAC-SHA-256 and a ~30-line HKDF verified against RFC 5869 vectors are all in the JDK; SunJCE GCM is AES-NI accelerated. BouncyCastle is a large, regularly-CVE'd dependency with FIPS/export variants and a provider install that conflicts with host applications, and the domain package may not import a crypto library at all. Zero crypto dependencies in `-core`; vendor SDKs live only in Pro adapters.
19. **A failed `PostErasureHook` makes the erasure `PARTIAL`, never `COMPLETE`.** Hooks run after the key destruction commits, so they need retry state; per-hook outcomes go into the erasure record and the proof-of-erasure refuses to render "complete" while one is outstanding.

**Threats section additions.** Wrapped-key resurrection by an insider who snapshots the key table before erasure and restores it after — the honest bound of the whole technique. Blind index as an offline dictionary against a low-entropy field (email), and as an equality/frequency oracle even without the key. Key-store outage misread as erasure. Hibernate dirty checking re-writing a shredded column. Second-level cache and an open session outliving an erasure. Cross-tenant key reuse for an identical subject id. Erasure race with a concurrent flush. Chain HMAC secret stored beside the datasource password (then it is not a second factor — B's rule).

**Spec lines that are wrong, with replacements.**
- *"destroys the subject's data key (overwrite + delete)"* → "deletes the subject's data key row and writes the `ErasureRecord` in the same transaction; overwriting first is theatre under MVCC and is not done."
- *"return a typed `ErasedValue` sentinel (configurable: null, placeholder, or exception)"* → "returns `ErasedValue` by default; `exception` is allowed; `null` requires an explicit property and WARNs at every startup."
- *"per-subject data key (AES-256-GCM, random 96-bit nonce per value, AAD = entity+field+subject)"* → add "random, never derived from the master"; AAD per control 2 (length-prefixed, with tenant and key version).
- *"optional blind index"* → optional **feature**; once enabled, its key is required and erasure nulls its columns.
- *"Property test: 100k encryptions, no nonce collision"* → this test cannot fail even against a badly broken RNG (100k draws from 2^96 collide with probability ~2^-64). Replace with: nonce source is `SecureRandom`, the per-key counter refuses at 2^32, and a stubbed narrow RNG is *detected*.

**Residuals — documented in `SECURITY-NOTES.md`, not engineered away.** Base backups, PITR archives and WAL segments hold wrapped keys until their retention expires — the erasure is complete only at `erasedAt + shredding.erasure.backup-retention`, and the proof-of-erasure states that date. Streaming replicas and logical-decoding slots hold the same. MVCC dead tuples survive until VACUUM. JVM heap dumps, core dumps and swap hold unwrapped data keys and plaintext. A cluster node's cache holds an unwrapped key for up to the TTL. An insider who archives the key table defeats the scheme entirely; crypto-shredding protects against future access to live systems and to data-at-rest copies, not against that. Proof-of-erasure attests that a key was destroyed — not that no plaintext copy exists in logs, exports, a search index or a PDF the application itself produced.

**Probes I expect in the PR** (each must fail before the fix): `probe_a_wrapped_key_row_restored_after_erasure_decrypts_the_value`, `probe_field_and_entity_names_collide_in_the_aad`, `probe_ciphertext_moved_between_rows_still_decrypts`, `probe_reading_an_erased_entity_rewrites_the_column_on_flush`, `probe_second_level_cache_serves_plaintext_after_erasure`, `probe_entity_tostring_leaks_the_decrypted_value`, `probe_blind_index_still_matches_the_erased_subject`, `probe_blind_index_matches_the_same_value_across_tenants`, `probe_spel_expression_reaches_a_bean_or_a_static_type`, `probe_changing_the_subject_expression_moves_a_row_out_of_erasure_scope`, `probe_key_store_outage_reads_as_erased`, `probe_crash_between_key_destruction_and_the_erasure_record`, `probe_concurrent_write_encrypts_under_a_destroying_key`, `probe_an_unkeyed_or_unanchored_erasure_chain_reports_intact`, `probe_tenant_b_decrypts_tenant_a_value_for_the_same_subject_id`, `probe_core_reads_a_plaintext_column_as_plaintext`, `probe_master_key_appears_in_actuator_env`, `probe_encryption_passes_the_per_key_2_32_limit`, `probe_a_failed_post_erasure_hook_reports_complete`.
